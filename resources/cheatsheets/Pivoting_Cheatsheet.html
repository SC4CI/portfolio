1. Discover Internal Networks

ابدأ من الجهاز المخترق: هل عنده NIC أو Route إلى شبكة ما تقدر توصل لها مباشرة؟ هذه هي نقطة قرار الـPivot.

قاعدة مهمة: اكتشاف شبكة ثانية ≠ Pivot ناجح. النجاح يحتاج Route/Proxy ثم إثبات وصول فعلي لخدمة داخلية.
Linux — عرض الواجهات والعناوين VICTIM SHELL
ip addr
في اللاب الموثق، ظهور واجهة شبكة ثانية كان الـTrigger لبدء Pivoting.
وجود NIC ثانية وحده لا يعني أن الـPivot نجح؛ هي فقط تكشف فرصة لشبكة داخلية.
Linux — عرض جدول التوجيه VICTIM SHELL
ip route
حدد الـsubnet الداخلي والـgateway من معلومات حقيقية ظهرت على الجهاز.
Windows — عرض الواجهات WINDOWS CMD
ipconfig /all
عرض الجيران المعروفين على Linux VICTIM SHELL
ip neigh
قد يساعدك في تحديد Hosts داخل الشبكة الثانية بدون افتراض أن كل العناوين حية.
Meterpreter — تأكيد Session الحالية METERPRETER
getuid sysinfo
تأكد أنك داخل الجلسة الصحيحة قبل تعديل Routes.
Meterpreter — إضافة Route للشبكة الداخلية METERPRETER
run autoroute -s [SUBNET]
استخدم الـsubnet الحقيقي المكتشف من ip addr/ip route، وليس عنوان Host مفردًا.
أمر autoroute وحده لا يثبت نجاح end-to-end؛ لا تعتبر إضافة Route وحدها نجاحًا.
اختبار SSH Credential معروف على Pivot Host KALI TERMINAL
ssh [USERNAME]@[TARGET]
إذا نجح الدخول، يمكنك استخدام -L أو -D أو -R حسب المسار المطلوب.
اختبار SSH Private Key معروف KALI TERMINAL
chmod 0400 [PRIVATE_KEY] ssh -i [PRIVATE_KEY] [USERNAME]@[TARGET]
استخدم مفتاحًا حصلت عليه من نفس اللاب أو مصدر مصرح.
مراجعة الشبكة على Pivot Host قبل الانتقال VICTIM SHELL
ip addr ip route
بعد إثبات الوصول، انتقل إلى Cheatsheet الخدمة الداخلية المكتشفة. لا تعيد Enumeration عام كامل هنا.

2. Meterpreter / Metasploit Routing

بعد معرفة الشبكة الداخلية، افحصها بالطريقة المتوافقة مع نوع الـPivot. لا تفترض أن كل Scan يعمل عبر SOCKS.

إذا عندك Meterpreter Route فقط بدون SOCKS، استخدم Metasploit scanners. إذا عندك SOCKS/SSH Dynamic Forward، استخدم أدوات TCP التي تتوافق مع ProxyChains.
Windows — عرض جدول التوجيه WINDOWS CMD
route print
إذا ظهر Subnet إضافي أو Route غير موجود عند جهازك المهاجم، سجله كمرشح للـPivot.
Metasploit — عرض Routes قبل الفحص MSFCONSOLE
route print
تأكد أن الـsubnet الداخلي موجود في Routing Table الخاصة بـMetasploit قبل تشغيل scanners.
Metasploit — فحص TCP عبر Route داخلي MSFCONSOLE
use auxiliary/scanner/portscan/tcp set RHOSTS [SUBNET] set PORTS [PORT] run
هذا المسار مناسب بعد إضافة Route داخل Metasploit؛ استخدم البورتات التي تهم هدف اللاب.
Metasploit — التحقق من Routes MSFCONSOLE
route print
لا تنتقل للفحص الداخلي قبل رؤية Route المناسبة.
Meterpreter — إضافة Route METERPRETER
run autoroute -s [SUBNET]
نفّذها فقط بعد التأكد من الشبكة الداخلية.
تأكيد Route في Metasploit MSFCONSOLE
route print
احتفظ بالـsubnet والـsession المرتبط بالـRoute.

3. SOCKS + ProxyChains

حدد نوع الـPivot المتاح: Meterpreter Route، SOCKS Proxy، أو SSH Tunnel. بعدها تحقق من المسار قبل التوسع.

Decision Flow: Second NIC/Subnet → Route أو SOCKS/Tunnel → تحقق من Route → اختبر Host/Port داخلي → استخدم Cheatsheet الخدمة المكتشفة.
ProxyChains — فحص TCP Connect محدود عبر SOCKS KALI TERMINAL
proxychains nmap -sT -Pn -n -p[PORT] [TARGET2]
استخدم TCP Connect فقط. SYN/UDP/OS detection لا تعمل بشكل موثوق عبر SOCKS/ProxyChains.
فحص خدمة داخلية واحدة بعد معرفة بورتها KALI TERMINAL
proxychains nmap -sT -Pn -n -sV -p[PORT] [TARGET2]
Version detection عبر ProxyChains قد يكون أبطأ أو غير كامل. لا تعتبر timeout دليلًا أن الخدمة مغلقة.
اختبار وصول TCP مباشر عبر ProxyChains KALI TERMINAL
proxychains nc -nv [TARGET2] [PORT]
مفيد كاختبار بسيط قبل تشغيل أداة خدمة متخصصة.
البحث عن SOCKS Proxy Module في Metasploit MSFCONSOLE
search socks_proxy info [SOCKS_MODULE] show options
اسم وخيارات الـModule قد تختلف حسب إصدار Metasploit؛ اعتمد على search/info.
اختبار خدمة داخلية عبر ProxyChains KALI TERMINAL
proxychains nc -nv [TARGET2] [PORT]
لا تستخدم Password Spraying عبر Pivot لمجرد وجود خدمة داخلية؛ انتقل لملف الخدمة واختبر فقط ما يسمح به الـScope.
Metasploit — تشغيل SOCKS Proxy بعد اختيار Module مناسب MSFCONSOLE
use [SOCKS_MODULE] show options set SRVHOST 127.0.0.1 set SRVPORT [SOCKS_PORT] run
راجع show options في نسختك؛ SOCKS version والإعدادات تختلف حسب الـModule.
شغّل Proxy محليًا فقط ضمن جهاز الاختبار ولا تفتح Listener أوسع من اللازم.

4. SSH Tunneling

الـPivot نفسه لا يحتاج Brute Force. اختبر فقط Credentials معروفة عندما يكون SSH أو خدمة وسيطة هي طريقك للشبكة الداخلية.

Credential reuse هنا هدفه إنشاء قناة وصول شرعية داخل اللاب، وليس جمع Credentials جديدة. Credential Access له ملف مستقل.
SSH — Dynamic SOCKS Proxy KALI TERMINAL
ssh -D [SOCKS_PORT] [USERNAME]@[TARGET]
استخدمه مع ProxyChains للوصول إلى عدة خدمات TCP داخل الشبكة.
SSH — Remote Port Forward KALI TERMINAL
ssh -R [REMOTE_PORT]:[TARGET2]:[PORT] [USERNAME]@[TARGET]
يفتح منفذًا على الجهة البعيدة ويوجهه للوجهة المحددة. استخدمه فقط عند حاجة واضحة داخل اللاب.

5. Port Forwarding

في Pivoting، “الاستغلال” العملي هو تحويل جلسة موجودة إلى مسار شبكة يعمل ثم استخدامه للوصول لخدمة داخلية موثقة.

لا تخلط المفاهيم: Route فقط = Pivot configured. إثبات الوصول بخدمة داخلية = Pivot working. استغلال الخدمة الداخلية نفسها ينتقل إلى Cheatsheet تلك الخدمة.
SSH — Local Port Forward KALI TERMINAL
ssh -L [LOCAL_PORT]:[TARGET2]:[PORT] [USERNAME]@[TARGET]
بعد الاتصال، استخدم 127.0.0.1:[LOCAL_PORT] للوصول للخدمة الداخلية المحددة.
SSH Local Forward — الوصول لخدمة داخلية عبر localhost KALI TERMINAL
ssh -L [LOCAL_PORT]:[TARGET2]:[PORT] [USERNAME]@[TARGET]
بعدها افتح العميل المناسب على 127.0.0.1:[LOCAL_PORT] بدل الوصول المباشر لـ[TARGET2].
Meterpreter — Local Port Forward METERPRETER
portfwd add -l [LOCAL_PORT] -p [PORT] -r [TARGET2]
ينشئ Local Forward عبر جلسة Meterpreter إلى Host داخلي محدد.

6. Verification & Cleanup

أثبت أن المسار يعمل، سجّل الشبكة والخدمة التي وصلت لها، ثم انتقل لملف الخدمة الداخلية بدل تكرار الهجوم هنا.

لا تعتبر رؤية NIC ثانية أو كتابة autoroute نجاحًا نهائيًا. النجاح الحقيقي يحتاج إثبات اتصال فعلي بخدمة داخلية.
اختبار خدمة داخلية عبر Local Forward KALI TERMINAL
nc -nv 127.0.0.1 [LOCAL_PORT]
إذا كان Local Forward قائمًا، هذا يختبر وصول TCP إلى الخدمة الداخلية بدون كشفها مباشرة لجهازك.
ProxyChains — اختبار خدمة HTTP داخلية KALI TERMINAL
proxychains curl -I http://[TARGET2]:[PORT]/
إذا استجاب HTTP عبر الـProxy فهذا Proof عملي على وصول end-to-end لهذه الخدمة.
Meterpreter — عرض Port Forwards METERPRETER
portfwd list
تأكيد Forward في Meterpreter METERPRETER
portfwd list
إثبات وصول HTTP داخلي عبر Proxy KALI TERMINAL
proxychains curl -I http://[TARGET2]:[PORT]/
إذا رجع HTTP response من [TARGET2] عبر الـProxy فهذا يثبت وصولًا فعليًا لهذه الخدمة.
إثبات وصول TCP داخلي عبر Local Forward KALI TERMINAL
nc -nv 127.0.0.1 [LOCAL_PORT]
نجاح TCP connection على الـlocal port يعني أن الـforward وصل للوجهة المحددة.
إزالة Port Forward عند انتهاء الاختبار METERPRETER
portfwd delete -l [LOCAL_PORT] -p [PORT] -r [TARGET2]
نظف الـforward المؤقت بعد انتهاء الحاجة له داخل اللاب.
